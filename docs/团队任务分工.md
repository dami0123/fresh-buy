## 二、前置工作：负责人先做（同伴开工前必须完成）

### 0. 已知问题：商家端「发货」按钮当前失效（开工前必读）

**现象**：商家端订单管理页点「发货」→ 弹「目标状态不合法」→ 订单永远卡在待发货。

**根因**：订单状态机重新编号后，`ORDER_STATUS.FINISHED` 的值从 `2` 变成了 `4`，而 `cloudfunctions/updateOrderStatus/index.js` 的白名单仍是旧的 `ALLOWED_STATUS = [1, 2]`，于是传入的 `4` 被判为非法。前端 `sub-seller/pages/order-manage/order-manage.js` 的 `submitShip` 传的正是 `ORDER_STATUS.FINISHED`。

**处理决定：不修，由同伴 B 在实现拍照发货时整体替换。**

理由：新流程里「发货」本来就该是商家拍 3 张照片（`shipOrder` 云函数 + `ship` 页面），`updateOrderStatus` 按 CLAUDE.md 已标记 deprecated，注定要被删除。现在去修它等于白做，而且「发货不带照片」这个中间态与流程图矛盾。

**因此：**
- **同伴 B**：看到发货按钮报错不要排查，这是预期行为。你的 P0 任务「ship 拍照页 + shipOrder」做完后，把 order-manage 里调用 `updateOrderStatus` 的 `submitShip` 整个替换掉即可，替换完成后这个按钮自然恢复（变成跳转拍照页）。
- **同伴 A**：`updateOrderStatus` 已废弃，不要调用它，也不要因为发货按钮坏了而去改 `sub-seller` 下的任何文件（那属于 B 的地盘）。
- **负责人**：`cloudfunctions/updateOrderStatus/index.js` 第 12 行注释已过期（仍写着「0 待支付由 createOrder 初始写入」），在同伴 B 替换完该函数后一并删除文件或更新注释。

**临时演示需求**：如果中途需要给老师演示发货功能，临时把 `ALLOWED_STATUS` 改成 `[2, 3, 4]`、`submitShip` 传 `ORDER_STATUS.PENDING_CONFIRM_SHIP`，改完重新部署 `updateOrderStatus`。演示结束后按上面的方案由 B 替换。

### 1. 订单状态机（已完成：写进 utils/constant.js + CLAUDE.md）

现有 3 个状态不够用，已扩展为（**此项已完成**，constant.js 与 CLAUDE.md 均已同步，支付环节同时移除）：

```
1 待发货（下单即写入；售后判定重发时回退到此）
2 待确认发货（商家已传 3 张照片，等买家确认；驳回则商家重传，仍停在本状态）
3 配送中（买家已确认发货照片，等收货）
4 已完成（买家确认收货）
5 售后中（买家上传退货照片，AI 鉴别/责任判定/退款或重发决策进行中）
6 已关闭（退款完成，订单终结）
```

重发货 = 售后环决议为「重发」时，订单状态回退到 1，并在订单里累加 reshipCount。

orders 集合需新增字段（一并写进 CLAUDE.md 数据库规范）：

```
address        Object   下单时的收货地址快照（不要引用 users.address，防止改地址污染历史订单）
shipPhotos     Array    商家发货照片 fileID，固定 3 张
shipRejectReason String 买家驳回原因（可空）
receiveAt      Date     确认收货时间
return         Object   售后子对象 { photos[], aiResult{}, liable(Boolean), resolution('refund'|'reship'), refundAt }
```

### 4. 三个决策（已拍板，详见 CLAUDE.md）

1. **支付**：**完全去掉支付环节**。确认下单后订单直接进入「待发货」，等待商家上传发货图。不做 `mockPay`，不接微信支付（需企业商户资质，课程项目无法申请）。现有代码中三处「待支付」残留需按 CLAUDE.md「支付环节移除的改造点」清理。
2. **AI 鉴别**：一期 mock，但判定规则必须**确定性、可复现**，禁止随机数。接口形状按真 API 设计，二期可替换。
3. **责任判定主体**：**系统自动终局判定**。商家端流程图里的「查看 AI 判定结果 → 是否商家责任」表示商家只是查看，**不提供人工判定按钮，不能改判**。`liable=false` 时订单自动回退到 4（已完成）并提示买家「售后未通过」，避免订单卡死。

## 五、联调清单（两人 + 负责人一起跑）

1.  happy path：下单（直接进入待发货）→商家拍 3 张→买家确认→确认收货→已完成
2.  驳回环：买家驳回→商家看到原因→重拍→买家确认
3.  售后-退款：收货后发起退货→AI 结果→商家判责→买家选退款→状态 6
4.  售后-重发：同上但选重发→订单回状态 1→商家再拍 3 张→走完收货
5.  越权抽查：买家账号直接调 shipOrder/updateProduct 应被拒；非本人调 confirmShipment 应被拒
